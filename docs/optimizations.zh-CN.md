# 技术报告：Ada 上的 DLSS5 推理加速

[English](optimizations.md)

## 摘要

本报告说明如何在保留 DLSS5 数值运算与数据依赖的前提下，改善社区兼容路径在 Ada 上的
执行效率。主要方法是重建异步复制完成协议、缩短寄存器活跃区间、复用融合 FFN 的输入片段，
以及联合选择寄存器预算、shared spilling 和线程块编译约束。
RTX 4080 的交替对照中，1080p / 1440p / 4K 的纯 NR 耗时分别下降 **5.35% / 9.11% / 10.30%**；
4K 独立进程对照下降 **8.16%**。实验设置与游戏内结果见第 9 节。

阅读顺序：第 1–2 节定义范围与成本模型；第 3–7 节展开具体方法；第 8 节说明接入；
第 9–10 节给出验证、结果与后续方向。硬件机制引用 NVIDIA 文档，网络结构引用社区研究，
资源统计和性能数字来自本项目记录。

## 1. 目标与系统边界

Faster DLSS5 是基于 [RenoDX DLSS5](https://github.com/RankFTW/rhi-repo) 的
Ada / RTX 40 加速补丁。优化目标是神经渲染执行：保留模型数值运算、MMA 累加顺序与
数据依赖，调整数据搬运、寄存器活跃区间及调度方式，使其更适合 Ada。

社区 base 负责游戏接入、NR 运行库、模型参数、图像分区和 padding。
我们的适配层在原有网络调用位置选择优化函数，沿用原始资源绑定、参数缓冲区和启动描述符。
因此，即使一个算子已经高度融合，也可以在保持外部契约的同时改变内部数据的暂存与消费方式。

网络结构的背景阅读采用社区开源项目 [MLX-DLSS](https://github.com/iamwavecut/MLX-DLSS) 的
[模型恢复说明](https://github.com/iamwavecut/MLX-DLSS/blob/main/docs/recovery-notes.md)：
下采样与 decoder 的连接、attention / FFN 的组织，以及
[时序处理参考](https://github.com/iamwavecut/MLX-DLSS/blob/main/docs/recovery-notes.md#temporal-command-line-reference)
均可从这些资料继续阅读。下文用 encoder、ViT、decoder 和时序 Pre/Post
指代相应的优化区域，重点讨论它们在 Ada 上的执行方式。

选定组合覆盖上述区域。
一轮时序网络可替换 **145 次内部调用和 2 次 Pre/Post 调用**。
包中包含 **45 个内部二进制变体和 2 个表面内核**：调用次数与二进制数量不同，
因为多个调用会复用同一个二进制，部分尺寸也会选择专用变体。

本文的 CTA 指一个 CUDA 线程块，warp 包含 32 个线程，lane 指其中一个线程位置；
MMA 指矩阵乘加，FFN 指前馈网络。讨论分块时，N 表示输出列方向，K 表示归约方向。

## 2. 成本模型：为什么能运行仍可能不够快

用于定位瓶颈的近似模型是：

`T内核 ≈ max(T张量计算, T搬运) + T未被隐藏的依赖等待 + Tspill + T指令发射`

这些项不是互相独立的可加计数器。复制、计算和访存服务可以重叠，改变一个 tile
可能同时影响多项成本。因此，我们结合编译资源信息和运行测量判断方案，
不会只按指令数量给候选排序。

NVIDIA 的 Ada 调优指南给出，计算能力 8.9 的每个 SM 可驻留 48 个 warp，
拥有 64K 个 32 位寄存器和 100 KB shared memory。
寄存器或 shared memory 分配可能先于算术吞吐限制活跃 CTA 数量。
[NVIDIA Ada 调优指南](https://docs.nvidia.com/cuda/ada-tuning-guide/index.html)

对于每 CTA 有 `B` 个线程、每线程约分配 `R` 个寄存器的情况，
`floor(65536 / (B × R))` 可以作为寄存器容量约束下 CTA 数量的初步上界。
实际还受分配粒度、warp/block 上限与 shared memory 限制。
所以，提高寄存器数量虽然可能减少 spill，也可能减少可用于隐藏延迟的 warp。
本文有关 occupancy 的解释来自容量模型与编译信息，并非直接测量 D3D 命令列表的驻留情况。

## 3. 异步搬运：从 Blackwell bulk copy 到 Ada 流水线

### 3.1 两代 GPU 的相关差异

这里比较的是 GeForce RTX 50 的 Blackwell **计算能力 12.0（sm_120）** 与 RTX 40 的 Ada
**计算能力 8.9（sm_89）**。数据中心 Blackwell 的 10.x 应按其自身能力分析。
[NVIDIA GPU 计算能力表](https://developer.nvidia.com/cuda/gpus)

| 机制 | RTX 50 / Blackwell | RTX 40 / Ada | 对适配的影响 |
|---|---|---|---|
| 逐线程 global → shared 异步复制 | 支持 `cp.async` | 支持 `cp.async`，每线程每次 4、8 或 16 字节 | Ada 已有可直接利用的异步路径 |
| TMA（Tensor Memory Accelerator）/ bulk copy | 支持相应的批量搬运路径 | 不支持 `cp.async.bulk` | 需要重新分配发起复制的线程及地址计算 |
| 搬运完成记录 | 可用 transaction barrier 跟踪完成字节数 | 可将普通 `cp.async` 的完成关联到 CTA 内的 barrier | 需要重建等价的完成协议 |

CUDA 将逐线程 LDGSTS 路径与 TMA 路径分别说明。前者从计算能力 8.0 起提供硬件支持，
能够直接把 global memory 数据送到 shared memory；TMA 从 9.0 起提供批量搬运。
TMA 的线性复制与使用 tensor map 的多维复制也应分开分析：下面的 512 字节案例是线性搬运。
[CUDA 异步数据复制](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/async-copies.html)

**TMA、cluster 和 barrier 分别解决不同问题。** Cluster 组织多个 CTA 并支持访问组内其他
CTA 的 shared memory；barrier 表达参与者与异步工作的完成依赖。
bulk copy 本身并不要求多个 CTA 协作。下述优化处理的是 CTA 内搬运；判断其他入口是否
依赖 cluster，需要结合启动配置和目标地址归属。
[NVIDIA Blackwell 调优指南](https://docs.nvidia.com/cuda/blackwell-tuning-guide/index.html)

### 3.2 为什么兼容适配会损失重叠

在本项目核对的 512 FFN 搬运点，原路径选出一个 lane 发起 512 字节 bulk copy，
并通过 transaction barrier 记录预期完成的字节数。适配到 Ada 后，同一段数据由一个
warp 的 32 个 lane 协作搬运。这样仍能得到相同的数据，但执行组织发生了三项变化：

1. **地址计算分散到各 lane。** 每个 lane 都要计算自己的源、目标偏移；这些地址与谓词
   会同矩阵片段争用寄存器。直接异步写 shared 可以省去中转数据寄存器，地址计算仍有成本。
2. **过早等待会截断重叠。** 在逐线程复制后立即 `commit_group; wait_group 0`，
   会让发起线程先等完复制，再继续本可独立执行的算术。保留了异步指令，却缩短了可隐藏延迟的区间。
3. **完成计数必须转换。** “512 字节传完”与“若干线程到达”是不同的计量单位。
   将 bulk 指令拆开之后，还要让消费者看到全部复制完成，而不是只看到发起线程到达。

Transaction barrier 同时跟踪线程到达和异步事务量；普通异步 barrier 则可通过关联复制的
完成来延迟当前 phase 的结束。这是迁移完成协议的基础。
[CUDA 异步 barrier](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/async-barriers.html)

### 3.3 Ada 如何接住同一个 512 字节 tile

保留的 512 FFN 实现对两个静态 bulk-copy 位置采用以下映射；512 pooling 的四个位置
采用同类方法。这里的“位置”是内核中的静态复制点，循环可以重复执行它。

| 项目 | Ada 上的处理 |
|---|---|
| 分工 | 搬运 warp 的 lane `i` 处理 `[16i, 16i + 15]`，`i = 0…31` |
| 总量 | `32 × 16 = 512` 字节，覆盖原来的连续区域 |
| 搬运 | 每 lane 发出 `cp.async.cg.shared.global`，目标仍为原 shared tile |
| 完成关联 | 每个参与 lane 将此前复制关联到原有消费者使用的 barrier |
| 消费 | 保留消费者的 phase 等待和 tile 布局，再执行原有矩阵运算 |

本项目使用不带 `.noinc` 的 `cp.async.mbarrier.arrive`：登记时增加当前 phase 的 pending count，
此前复制完成后再异步减回。因此，原有普通线程到达计数可以保留，复制完成另行被跟踪。
消费者通过成功的 `mbarrier.test_wait` 确认相关 phase 完成。这个关联指令从 SM 8.0 起可用。
[PTX ISA：cp.async.mbarrier.arrive 与 mbarrier.test_wait](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html)

实现中还将对应等待改为 Ada 支持的形式，并保留普通到达操作的数量。
复制登记必须发生在该 phase 最后一次普通到达之前，避免 barrier 过早进入下一轮。
因此，改动单位是“复制发起、完成登记、普通到达、消费者等待”这一整段依赖关系。

完整 512 字节 tile 的源、目标均满足 16 字节对齐。对于带边界分支的其他位置，
还要保留原有有效字节与补零行为；只跳过越界 lane 可能留下上轮 shared 数据。
`cp.async.cg` 使用的缓存策略也不自动保证更高吞吐，需要结合实际访问复用判断。
[CUDA 复制宽度、对齐与缓存路径](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/async-copies.html)

### 3.4 在消费边界等待，让下一块搬运与当前计算重叠

这里区分两个时刻：**数据就绪**决定何时可以读，**读者结束**决定何时可以覆盖缓冲区。
双缓冲需要同时维护这两个依赖；下一轮写入不能越过当前读者。
[CUDA producer/consumer barrier 模式](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/async-barriers.html)

下面是解释调度关系的双缓冲示意，`A`、`B` 为两个 shared tile：

```text
预热：搬运 tile 0 → A；等 A 就绪
轮次 0：发出 tile 1 → B；计算 A；读 A 结束；等 B 就绪
轮次 1：发出 tile 2 → A；计算 B；读 B 结束；等 A 就绪
……
收尾：计算最后一个已就绪 tile；所有读写完成后结束
```

若每块搬运耗时 `L`、计算耗时 `C`，完全串行的简化模型为 `N(L + C)`；理想流水线为
`L + (N − 1)max(L, C) + C`。这是解释重叠上限的模型：实际还包含发射、同步、带宽竞争和
资源占用成本。独立算术越少，可隐藏的搬运延迟越少；增加缓冲深度也会增加 shared 占用。

使用 CUDA C++ 编写同类内核时，可用 `cuda::memcpy_async` 配合 `cuda::pipeline`：
生产者 acquire 空闲阶段、提交复制，消费者在使用阶段前 wait，读完后 release。
共享 pipeline 的 commit 等操作应保持参与 warp 收敛，避免分支使批次计数和等待范围扩大。
本项目在已有融合内核中直接衔接其 barrier 和暂存区，保留原有数学与布局。
[CUDA pipeline 生命周期与 warp entanglement](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/pipelines.html)

### 3.5 与寄存器优化一起衡量收益

更早发出复制会延长某些地址、phase 状态和待用片段的存活时间。因此，我们同时调整
加载位置与寄存器分配，确认恢复的重叠没有被新增 spill 抵消。第 4 节说明活跃区间，
第 5 节说明融合 FFN 内的数据复用。

包含 12 个入口的异步/资源组合，在交替和独立进程测量中带来了约
**2.93–3.55% 的完整 NR 降耗时**。这个数字对应整个组合；各模块及当前整网结果分别见
下文和[性能报告](benchmarks.zh-CN.md)。

## 4. 寄存器压力、uniform lowering 与 local spill

### 4.1 从同时存活的值定位压力

核心指标是同一时刻存活的值有多少。
过早加载的输入片段可能跨越地址构造、同步和其他矩阵运算一直占用寄存器。
将不可变数据的加载移近使用位置，可以缩短这些活跃区间，同时保持算术顺序。

寄存器优化结合三种选择：

1. 将片段加载移近消费者。
2. 在能减少重复装载的位置，保留跨 MMA 的有效复用。
3. 在完整融合内核中对比寄存器上限和编译器分配结果。

512 通道输入/输出投影的保留实现，将一次提前加载八个片段改为逐次加载当前消费的两个片段。
64 条 MMA 的顺序保持不变，128 寄存器上限也保持不变。
这减少了“已经加载、尚未使用”的片段在地址计算和其他 MMA 期间占用寄存器的时间。

| 投影样本 | 等待式适配 stack | 保留实现 stack | 实际寄存器/线程 | shared/CTA |
|---|---:|---:|---:|---:|
| 512 输入投影 | 80 B | 0 B | 126 | 12,312 B |
| 512 输出投影 | 80 B | 0 B | 123 | 12,312 B |

保留实现的 local load/store 指令消失，shared 容量未增加：该例消除了溢出需求，
没有把这批值迁移到 shared。相比只看 stack 数字，同时检查实际寄存器、访问指令和 shared
大小，才能区分“减少活跃值”与“更换 spill 位置”。

### 4.2 Uniform lowering 为什么要结合活跃区间看

Uniform lowering 是问题的一部分，但需要准确描述。
审计发现 **24 个入口中 132 处 uniform FP8 零值转换**在 Ada 路径中改变了表示方式；
将 uniform 指令纳入后，总转换数量仍然一致。
Ada 也有 uniform-register 设施。证据指向 lowering 差异和普通寄存器压力，
不能解释成 RTX 40 没有 uniform register，也不能直接推导出 32 倍开销。

这类差异的优化意义在于：编译到不同目标时，常量、转换结果和地址状态可能占用不同的
寄存器类别、产生不同长度的依赖链。即使数值转换总量不变，与矩阵累加器同时存活的普通值
仍可能增加。因此我们检查生产者到最后消费者的范围，再调整附近加载与复用，
而不是仅按 uniform 指令数预测收益。132 处是审计覆盖量，不是 132 项独立加速贡献。

### 4.3 寄存器上限、实际分配和驻留能力

寄存器上限是编译约束，实际分配可能更少。例如选定 512 FFN 的上限为 128，
实际使用 118 个寄存器并且零栈。另一类内核则允许少量 spill 来换取更低的每线程分配。
按第 2 节的容量模型，256 线程 CTA 在 168 寄存器/线程时仅寄存器容量上界为一个 CTA，
128 寄存器/线程时为两个。这说明为什么“降低寄存器预算”也能加速；实际驻留仍需结合
该内核其他资源约束判断。

最终目标是降低执行耗时。寄存器上限、加载位置与数据复用需要组合选择，
在 spill 流量和活跃 warp 容量之间取得合适的平衡。

## 5. 融合 FFN、投影及边界调度

### 5.1 在融合内部改变复用，不拆开整个算子

融合内核包含多个内部计算阶段。优化其中一段不必改变其 API 边界。
我们围绕输入片段复用、加载位置和资源分配工作，保留数值操作顺序以及下一阶段期待的内存布局。

以选定 256 FFN 的扩展阶段为例，将相邻两个 N32 输出切片配对为内部 N64 分组。
对每个 K 步只加载一次输入片段 A，分别与两个输出切片的 B 片段运算：

```text
对相邻输出切片 n、n+1：
    按原来的 K 顺序：
        加载 A[k]
        用 A[k]、B[n,k] 更新切片 n
        用同一 A[k]、B[n+1,k] 更新切片 n+1
    按原顺序完成切片 n 的激活、转换与收缩
    按原顺序完成切片 n+1 的激活、转换与收缩
```

这样减少扩展循环中的 A 装载，B 数据量和矩阵运算量保持不变。N64 指内部输出分块宽度，
网络的通道数不变。第二个切片需要独立累加器，因此收益取决于节省的装载能否覆盖新增
活跃值的成本。每个结果的 K 累加顺序、收缩阶段的切片累加顺序、FP8/FP16 转换与输出布局均保留。

### 5.2 将同类方法应用到尺度边界

边界内核还承担上下采样或投影，必须保留其前后处理和同步。最终在 256 输入/输出边界
保留 N64 输入复用与延后 shared 加载，在 256 下采样/上采样保留原执行分块并调整寄存器预算。
因此，同一通道数下的四个边界也采用不同的最终组织。

延后加载只跨越不依赖该片段的计算，不能跨越修改源数据的写入、异步复制或同步边界。
选定 Input128 延后 40 条静态 shared 装载，Down64 / Up64 分别延后 16 / 32 条；
Input256 / Output256 分别延后 44 条并结合 N64 复用。这里统计的是移动的指令位置，
并未将这些加载全部删除。

512 FFN 则组合第 3 节的异步完成、128 寄存器上限和 `mma_throughput` 编译提示；
选定 pooling 使用异步完成与独立资源预算。编译提示由编译器决定具体排程，
收益以整个保留组合的回放结果记录。

### 5.3 模块测量

较大的局部收益集中在网络深层：

| 测量组 | 局部调用回放耗时合计下降 | 测量口径 |
|---|---:|---|
| 512 FFN，15 次调用 | 39.11% / 39.74% | 相对社区，两种顺序 |
| 512 pooling | 16.29% / 16.45% | 同轮局部测试 |
| 完整 512 组，66 次调用 | 22.31% / 22.18% | 局部调用中位数求和 |
| ViT 计算，40 次调用 | 12.29% / 12.40% | 模块测试 |
| 选定的 256 边界 | 19.02% / 18.89% | 边界测试 |

这些组存在重叠，各轮也有自己的对照组合，不能相加成为最终 NR 收益。
Hot replay 会反复使用同一算子和资源；完整推理还包含相邻计算、依赖关系和缓存驻留变化。

128/64/32 等较小阶段，每单位调度和暂存开销对应的计算更少，
因此需要结合通道数与尺寸选择执行组织。

## 6. Shared memory：选择值得迁移的访问

### 6.1 让编译器分配 spill 存储

Local spill 由设备内存支持，但访问可能命中缓存。
迁移到 shared memory 会改变访问路径，同时增加片上容量、寻址、bank 布局及潜在同步成本。
单看空闲容量无法判断哪条路径更快。

CUDA 13 引入的 `enable_smem_spilling` 允许 PTXAS 优先将 spill 放入 shared，不足时仍可使用
local memory。编译器管理槽位与活跃期，无需手工逐个挑选变量。它适用于相应的 whole-program
编译模式，并要求避免动态 shared 等不支持的组合；launch bounds 也会影响分配估计。
[NVIDIA：shared-memory register spilling](https://developer.nvidia.com/blog/how-to-improve-cuda-kernel-performance-with-shared-memory-register-spilling/)

本项目联合选择 spill 策略、寄存器预算与合法的线程块编译约束。
“最大编译线程数”是编译器允许的上界，并非运行时一定启动这么多线程；“固定线程块”则
约束实际启动尺寸。下面的 attention 和 downsampling 保持原线程数运行，
让编译器在新的合法上界下生成 spill 布局。

### 6.2 保留实现的资源变化

| 保留类别 | 实际线程/CTA | 编译约束 | shared/CTA 前 → 后 | stack 前 → 后 | 容量计算的 CTA/SM 前 → 后 |
|---|---:|---|---:|---:|---:|
| ViT attention | 128 | 最大线程数 256，自动 shared spilling | 8,208 → 16,400 B | 32 → 16 B | 4 → 4 |
| 512 pooling | 128 | 固定原 128 线程块 | 8,208 → 8,208 B | 88 → 56 B | 4 → 4 |
| 256 downsampling | 256 | 最大线程数 512，自动 shared spilling | 16 → 30 KiB | 24 → 0 B | 2 → 2 |

资源变化来自该轮相对于既有优化实现的编译统计与容量查询，CTA 数表示资源允许的容量。
这三个选择在增加暂存或改变代码生成后，保留了原有容量上限。

Shared-memory 收敛最终保留三个小范围类别、共十次调用：

| 保留类别 | 相对已优化组合的局部追加降耗时 | 解释 |
|---|---:|---|
| 8 次 attention | 1.12–1.25% | 选定的 shared-memory / 资源组织调整 |
| 512 pooling | 2.05–2.42% | 固定 block 代码生成；pragma 开关二进制完全一致 |
| 256 downsampling | 0.52–0.83% | 小幅可重复局部收益 |

Pooling 的控制实验将机制定位为固定 block 代码生成。
Shared-memory 改动结合周围的寄存器与同步成本，以实际执行收益决定保留范围。

### 6.3 为什么还要看访问成本

Shared spilling 保留每个线程私有值的语义，不能将这些槽位当成跨线程共享数据。
对于跨线程复用的 tile，才需要另外维护生产者/消费者同步。两者虽然占用同一类物理资源，
生命周期和用途不同。

本轮机制证据是编译资源变化、相同编译约束下的开关对照及完整内核计时。
未新增 bank-conflict 或动态 spill 字节计数，所以不能从静态 stack 的下降计算出节省的 DRAM 流量。
当 shared 使 CTA 容量下降，或增加了地址与访问指令时，收益需要由完整内核时间决定。

## 7. 时序 Pre/Post 与尺寸处理

### 7.1 保留采样数学，调整资源组织

Pre/Post 处理内部网络前后的表面输入输出。
选定的 Pre 保留原纹理访问调度，采用 128 寄存器上限及 local spilling，
时序帧局部重复测试下降 **6.60–9.82%**。
选定的 Post 使用 128 寄存器上限及 shared spilling，局部下降 **2.84–4.19%**。
没有历史的初始化路径等不符合所选时序契约的情况，沿用原生函数。

| 保留实现 | 实际线程/CTA | 实际寄存器/线程 | stack | 编译报告 spill store/load | shared/CTA |
|---|---:|---:|---:|---:|---:|
| 时序 Pre | 32 | 128 | 80 B | 80 / 80 B | 2,048 B |
| 时序 Post | 32 | 128 | 0 B | 0 / 0 B | 2,560 B |

两者均保留采样坐标、原纹理访问次序、FMA 与量化运算。Pre 与 Post 采用不同 spill 策略，
依据的是各自完整内核的表现。上表为编译统计；Pre 的 80 B 不代表每帧只发生 80 B 访存。

### 7.2 使用真实表面与历史验证

Pre 的输入包含纹理对象，Post 写入 surface，因此不能把它们当作普通线性指针回放。
局部验证保留实际纹理、history 与其他参数，为输出建立独立缓冲区或匹配格式的 surface。
每个分支开始前恢复完整输出与保护区，避免候选未写的位置继承对照数据。
验证既检查当前输出，也检查后续帧使用的历史状态；静态与运动输入均参与保留方案的评估。

### 7.3 将尺寸作为参数传递

适配层读取原生尺寸和 padding。此前四处尺寸常量折叠位置加入了通用变体，
遇到已知精确尺寸时仍可选择更快的特化路径。玩家不需要选择分辨率配置。
[尺寸设计及验证矩阵](dynamic-dimensions.zh-CN.md)。

## 8. 运行时集成与兼容性

玩家只需在社区插件旁安装一份内核包。适配层相对自身位置定位它，
正常启动游戏即可加载，无需自定义启动环境。
接入通过 ReShade addon API、已加载的 NR/NVAPI 入口协商完成。
安装器不按游戏名、精确显卡型号、驱动字符串或社区 base 整文件哈希设置白名单。

开始替换前，完整原生执行会核对完整网络序列，以及每个候选替换位置的参数布局、尺寸关系、启动几何和资源契约。
无历史初始化图先走原生，后续符合要求的时序图完成核对后，再启用替换。
每次实际调用继续检查其当前契约；不匹配的调用沿用社区函数。

接口与调用契约匹配可以支持兼容的打包或插件更新，但不能证明一个在相同接口下
改变数学运算的未知模型仍然等价。这是兼容研究有意义的技术边界。
包校验用于完整性和实验溯源，不是上游版本白名单。

Evaluate 转发通过尾跳保留原始返回地址，并在构建时检查生成汇编，以保持调用方身份与
原接入契约。替换发生在网络函数选择位置，社区插件继续负责呈现流水。

## 9. 验证与最终实测结果

### 9.1 实验层级与统计口径

| 层级 | 控制内容 | 记录指标 |
|---|---|---|
| 编译与资源 | 固定目标 SM、编译选项、线程块与候选身份 | 实际寄存器、stack、spill 指令、shared、容量上界 |
| 局部回放 | 相同捕获输入、恢复 scratch/状态、交替执行对照 | 完整内核时间；按调用中位数汇总模块 |
| 完整 NR | RTX 4080 / 驱动 616.56；固定合成 model1/sRGB 输入 | 每轮预热 100 帧、测量 400 帧；交替及独立进程结果 |
| 游戏 | 《赛博朋克 2077》2.31 官方 benchmark；同分辨率三组设置一致 | 原游戏、社区、优化各两次，报告 FPS 与新增整帧成本 |

完整 NR 的 ABBA 顺序是社区、优化、优化、社区；BAAB 反向安排。
表中交替 NR 值取两次运行各分支均值的平均，独立进程值取两次运行 P50 的平均。
局部调用回放采用自己的统计口径，不与整网均值混算。
游戏使用 High raster、原生 DLAA、SDR，关闭 RT、PT、RR、FG、动态分辨率、Reflex、
VSync 与帧率限制。详细输入与逐次汇总见[测试方法与数据](benchmarks.zh-CN.md)。

### 9.2 正确性验证

验证从编译资源检查、算子回放逐步推进到输出对比、完整推理和游戏测量。
内部组合曾对 **200 个捕获张量/输出、共 2.171 GB 数据**完成一致性对比。
表面内核另做验证；跨尺寸矩阵使用独立原生/优化进程，对静态、运动及 NR+SR 输入的最终图像进行比较：12 组对照，
每个进程三帧，共 72 帧，最终图像逐字节一致。

算子验证同时检查数值输出、读写 scratch、同步状态与保护区；Pre/Post 检查纹理与表面
输出及历史。跨尺寸最终图像比较补充了接口集成验证，与局部数值检查形成两个层次。

### 9.3 纯推理与游戏结果

| 分辨率 | 社区 NR → 优化 NR | NR 降耗时 | 游戏社区 → 优化 FPS |
|---|---:|---:|---:|
| 1920×1080 | 4.7539 → 4.4994 ms | 5.35% | 91.37 → 92.62 |
| 2560×1440 | 7.5083 → 6.8246 ms | 9.11% | 66.77 → 69.50 |
| 3840×2160 | 17.6821 → 15.8614 ms | 10.30% | 31.08 → 32.38 |

上表 NR 采用交替对照。4K 独立进程结果为 **18.2810 → 16.7892 ms，下降 8.16%**。
测试显卡 RTX 4080，驱动 616.56；游戏数据来自《赛博朋克 2077》benchmark。
计时样本在固定形状构建中测量选定优化。当前安装和契约检查改动有独立正确性记录，
不将这些验证转写为新的计时样本。

Amdahl 定律解释了整体收益的稀释：若某区域占基准耗时比例 `f`，
其自身耗时下降比例 `r`，忽略重叠与竞争变化时，整体下降约为 `f × r`。
占总耗时 25% 的区域加快到耗时下降 20%，整体理想下降是 5%。
不同基准、互相重叠区域的局部百分比也不能直接相加。

游戏新增成本按 `mean(1000/FPS开启) − mean(1000/FPS关闭)` 估算，先将各次 FPS 转为 ms
再求平均，包含接入及其与渲染的交互。
4K 测得 **16.714 → 15.416 ms**。公开 RTX 5070 Ti 的 **17 ms** 来自另一款游戏
《NBA 2K27》，作为背景参考，不能当成受控显卡速度比。
[测试方法与数据](benchmarks.zh-CN.md) ·
[TechSpot 参考](https://www.techspot.com/article/3170-real-dlss-5-performance/)。

## 10. 结果解读与后续方向

独立进程和交替测量都保留，因为缓存/历史、频率状态及运行顺序会影响小幅差值。
GPU 频率未锁定，交替分支共享历史状态；1080p 游戏提升较小且有波动。
最终图像一致性覆盖记录的输入，长期运动序列仍需要专门评估。

下一步优先改善暂存开销占比较大的低通道阶段，测量更多尺寸下的通用组合，
并验证契约兼容的社区更新。每项保留改动应具备明确局部机制、正确性结果及对照基准。
