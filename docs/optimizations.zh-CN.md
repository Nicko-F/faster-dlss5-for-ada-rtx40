# 针对 Ada 调整执行组织

[English](optimizations.md) · [中文主页](../README.zh-CN.md)

本项目以社区兼容路径为基础，保留数学运算、MMA 顺序和数据依赖，减少执行组织不适合 Ada
时产生的开销。这里公开方法和观察结果，不包含 NVIDIA 指令转储、完整启动参数或重建配方。

## 异步搬运

将 bulk copy 拆成较小拷贝后，如果每次拷贝都紧跟等待，就可能失去计算与搬运重叠。
保留的实验采用每 lane 16 字节异步拷贝与 barrier 完成计数，让消费者在真正使用数据时等待，
生产者此前仍可执行独立工作。复用缓冲区之前仍必须保证旧数据的读写依赖已经完成。

通用思路为：发起下一 tile 的拷贝 → 计算已就绪 tile → 等待下一 tile 就绪 →
旧 tile 的读取完成后交换缓冲区。这不意味着可以删除所有等待或模拟所有 Blackwell 设施；
可重叠程度仍由分块、shared memory、占用率和周围融合计算决定。

## 寄存器活跃区间、uniform lowering 和 spill

过早加载 fragment 会使大量值跨越无关计算仍然存活，提高通用寄存器压力，进而产生 local
memory 栈访问。我们将加载移近使用位置、缩短活跃区间，并同时检查寄存器分配与运行结果。

在具体的 512 通道输入/输出投影案例中，旧的等待式适配使用 80 字节栈，第一轮异步方案为
88 字节，精修方案降为 0；shared memory 仍为 12,312 字节，寄存器分别为 126 / 123，
检查到的 local load/store 被消除。**这仅指这些投影入口，不意味着整网没有 spill。**

兼容转换还改变了部分 uniform/scalar lowering：审计中 24 个入口的 132 处 uniform FP8
零转换改变了表示方式。把 uniform 指令算进去之后，总 FP8 转换计数仍一致。
不能把它解释成 32 倍成本，也不能说 Ada 没有 uniform register。目前没有隔离实验证明
所有 spill 都由 uniform 差异导致。

单纯加大寄存器上限可能降低占用率；消除栈也可能因额外指令或 staging 反而变慢。
因此先保留有证据的局部收益，再测试组合方案。

## Shared memory 与融合阶段

最近保留的 shared-memory 方案覆盖 10 次调用：8 个 attention、一个 512 通道 pooling、
一个 256 通道下采样。它是在已有优化上的小幅增益。没有保留“一律把 local 改成 shared”
的方案，因为 bank 布局、同步、指令数量和占用率都会影响速度；空闲容量不能直接推出性能收益。

此前还调整了融合 encoder、ViT、decoder 内的 fragment 复用和执行调度。不能宣称每个阶段
都已经达到最优。较小的 128/64/32 通道阶段和低分辨率具有不同的计算与固定开销比例，仍会继续研究。

## Pre/Post 与分辨率

当前组合在匹配计算图中替换 145 个 buffer 调用；历史输入齐全时再替换两个 Pre/Post 调用。
启动或无历史帧时保留原 Pre/Post。1080p 和 1440p 使用各自的编译 profile 和形状专用选择，
不能仅把任意 4K 内核换一个输入分辨率就使用。

替换受到运行库、形状、启动参数和输出格式条件约束。管理工具还检查测试过的社区文件、显卡和驱动。
替换日志仅证明路径选择，不证明所有时间上的画质一致，也不是 GPU 独立计时。

游戏对比中没有重新设计社区插件的插入流程；整帧成本包含插件同步与资源竞争。
纯 NR 和游戏使用不同输入及环境，不能直接相减得到插件开销。
预览不含接入 hook 实现和衍生 GPU 内核；`include/` 的原创 V1 声明只是接口说明。
